# Reflection Report — Scribble Lab

## What the Starter Already Had

The starter provided a working two-package monorepo (Express backend + React
frontend) with TypeScript, Vitest, and basic routing. It included room
creation and join endpoints, an in-memory room store, a branded landing
page, lobby and game page shells, and placeholder UI for the canvas, guess
form, scoreboard, and result panel. Seed data (5 words, 2 roles) was
pre-populated. No game logic, drawing, scoring, or multi-player sync was
implemented.

## What Was Added

**Scenarios 2–4** (game start, gameplay interaction, result and restart)
were fully implemented on top of the existing Scenario 1 (room setup and
lobby). This included:

- **Backend**: `startRoom`, `updateCanvas`, `submitGuess`, `restartRoom`
  with full validation (host-only, player count, role checks, empty guess
  rejection, case-insensitive comparison, duplicate correct-guess rejection,
  round-end detection). Types extended: `Round`, `Guess`, `Stroke`, `Point`,
  `RoomStatus`. Four new API routes: `POST /start`, `/canvas`, `/guess`,
  `/restart`. Error responses use machine-parseable codes.

- **Frontend**: Interactive `Canvas` component with pointer-coordinate
  scaling fix, read-only mode for guessers, and clear button. `GuessForm`
  with local validation, loading state, and error display. `Scoreboard`
  with live scores and drawer badge. `ResultPanel` with guess history and
  word reveal. `GamePage` rewritten with role-aware rendering for all
  three states (playing, result, redirect to lobby). Host identity
  preserved across refresh via three-level fallback
  (`stateViewerIsHost || room.viewerIsHost || hostParticipantId match`).

- **Testing**: 70 tests total (31 backend + 39 frontend) covering all
  game lifecycle operations, component rendering, error paths, and
  full round-trip scenarios. Bundle size: 59KB gzipped.

## Key Decisions

- **HTTP polling over WebSockets**: The lab explicitly prohibits WebSockets.
  A 2-second poll interval syncs all state. Canvas strokes use a 500ms
  debounced `POST` to batch updates.

- **Canvas as point arrays**: Strokes are serialised as `{ x, y }` point
  arrays rather than base64 images, keeping payloads small.

- **Deterministic word selection**: `STARTER_WORDS[(totalParticipants +
  roundNumber) % 5]` ensures reproducible per-round word choice.

- **Host = drawer for round 1**: The host is always the first drawer.
  Future rounds could rotate but that is out of scope per lab constraints.

- **Scores reset on restart**: Per lab scope — no multi-round score
  accumulation.

## AI Usage

All implementation code was generated by the AI assistant (opencode) through
interactive prompting. The assistant was provided with the full project
context, existing code, and specification artifacts. Each feature was
decomposed into ordered tasks and implemented incrementally with
verification (typecheck, tests, build) at each step. The assistant also
identified and fixed a canvas pointer misalignment bug and a host-identity-
after-refresh issue during implementation.

## Tradeoffs

- **No canvas snapshot thumbnail**: The canvas syncs full stroke arrays on
  every poll. For complex drawings this could be large, but for a simple
  word-guessing game the payload stays small.

- **No real-time feedback**: The 2-second polling means guessers see drawing
  updates with up to 2 seconds of delay. Acceptable per lab constraints.

- **All-guessers-correct ends round**: The round ends automatically when
  every guesser has guessed correctly. There is no timer or manual
  end-round — the drawer cannot control round duration.
