# Phase 0 Research: Room Setup & Lobby

**Feature**: 001-room-setup-lobby
**Date**: 2026-06-02

This document resolves every "NEEDS CLARIFICATION" candidate raised during plan
authoring. The spec arrived with three clarifications already integrated (host
identity persistence, no player cap, 4-letter A–Z codes), so the remaining
unknowns are implementation-pattern decisions, not behavioral ones.

## Decision: Polling implementation pattern

**Decision**: Use a `setInterval(fn, 2000)` inside a single `useEffect`, with a
`clearInterval` in the cleanup. The callback calls `roomStore.fetchRoom()`,
which already updates state and surfaces errors into `RoomState.error` without
throwing through to the UI tree.

**Rationale**:
- Matches Constitution Principle IV ("approximately 2 seconds") with a single
  visible knob (the `2000` literal).
- Cleanup on unmount satisfies FR-010 ("polling MUST stop cleanly when the
  viewer leaves the lobby screen") with no extra plumbing — React unmounts the
  Lobby route when the user navigates away.
- The starter already centralizes fetch state in `RoomStore`, so the hook
  simply triggers it; no new state machinery is added.

**Alternatives considered**:
- `setTimeout` recursion (self-scheduling) — buys backoff but adds complexity
  and a separate cancel flag; rejected because polling does not need backoff at
  lab scale and a single `clearInterval` is the cleanest unmount story.
- `useSWR` or React Query — would introduce a top-level dependency, prohibited
  by Constitution Principle II.
- Long-polling on the server — out of scope (would require server-side timing
  changes and complicates the in-memory model).

## Decision: Host identity persistence mechanism

**Decision**: `localStorage` only. Key `scribble:identity:<roomCode>`, value
serialized `{participantId: string, role: "host" | "guest"}`. Wrap every read
and write in a `try/catch` that degrades to in-memory only when the API throws
(private mode, locked-down embeds, storage quota).

**Rationale**:
- The spec's Q1 clarification explicitly chose browser-local storage keyed by
  room code (not a server-side session).
- `localStorage` survives tab refresh; `sessionStorage` does not, which would
  defeat the whole clarification.
- A single key per room avoids cross-room contamination and naturally clears
  when the user manually purges site storage.
- The `try/catch` keeps the no-auth, no-session constraint intact: failure of
  the storage layer is graceful, not fatal.

**Alternatives considered**:
- `sessionStorage` — lost on tab close and on some refresh paths; defeats Q1.
- IndexedDB — overkill for a single small JSON record.
- Cookies — would imply server-side identification and bleed toward "session,"
  which is on the constitution's forbidden list.
- Encoding identity into a URL fragment — fragile across user-driven URL
  edits; couples deep links to identity unnecessarily.

## Decision: Host designation as a server-authoritative field

**Decision**: Add `hostParticipantId: string` to the `Room` model and to the
`RoomSnapshot` returned by every endpoint. Server sets it once at room
creation; nothing rotates or reassigns it.

**Rationale**:
- The server is the only place that knows who created the room; trusting the
  client to claim host status would violate spec FR-014 and the constitution's
  determinism principle.
- One field is enough; we never need to enumerate "former hosts" or "next
  candidate."
- Exposing it in the snapshot lets every client derive `isHost` purely from
  the snapshot + its own local identity, with no separate endpoint and no
  custom auth header.

**Alternatives considered**:
- Boolean `isHost` per participant — denormalized and risks drift if a future
  feature ever reassigns host.
- Implicit "first participant in the array is host" — fragile; the
  participants array is intended as an ordered display list, not a host
  ledger. Reordering for any reason would silently change host identity.

## Decision: Room code character set and generation

**Decision**: 26-letter uppercase A–Z, 4 characters, generated by picking each
character uniformly with `Math.random()` and rejecting collisions with a loop
against the active rooms `Map`.

**Rationale**:
- Spec's Q3 clarification fixed the alphabet at A–Z and length at 4.
- 456,976 codes vastly exceed concurrent rooms expected in a lab setting,
  making rejection-loop iterations rare.
- Pure identifier; the Constitution's determinism rule applies to *game
  rules*, not to identifier generation, so `Math.random()` is appropriate.
- Existing starter code uses a wider alphabet (`A-Z` minus I/O + digits 2–9);
  we deliberately narrow rather than widen, matching the spec, even though it
  drops the "no ambiguous glyphs" trick. The trade is acceptable for a lab.

**Alternatives considered**:
- Keep the starter's 32-char readable alphabet — contradicts the spec
  clarification.
- Cryptographic randomness via `node:crypto.randomBytes` — overkill; we
  already accept that strong unguessability is not a goal (spec Assumptions).

## Decision: Error response shape

**Decision**: All error responses are JSON objects of shape `{message:
string}`. The existing `errorHandler` already does this; we extend it by
ensuring every error path inside `rooms.ts` produces a user-friendly message.
Specifically:
- Empty/whitespace-only code → 400 `{message: "Enter a room code"}`
- Unknown room code → 404 `{message: "Room not found"}`
- Generic invalid payload (any other Zod failure) → 400 `{message: "Invalid request payload"}`

**Rationale**:
- The frontend `api.ts` already extracts `.message` from error bodies; aligning
  the server contract makes the UI a one-liner per error.
- Matches FR-015 ("clear, plain-language strings") and the constitution's
  rule that raw error codes / stack messages must not surface.

**Alternatives considered**:
- Including a machine code (`{code: "ROOM_NOT_FOUND", message: ...}`) — useful
  for analytics; out of scope for a lab and not needed to satisfy FR-015.
- Exposing Zod's raw `issues` array — leaks implementation detail and is
  unfriendly UX.

## Decision: Lobby manual-refresh button

**Decision**: Remove the manual "Refresh Room" button from `LobbyPage.tsx`
once polling lands. Keep an inline error region for polling failures.

**Rationale**:
- Two-tab validation (Constitution Principle V) becomes ambiguous if a tester
  can mask a polling regression by pressing Refresh.
- The button exists only because the starter lacked polling; once FR-009 is
  satisfied it is dead weight.

**Alternatives considered**:
- Keep both — historical noise; encourages testers to bypass the gate.
- Hide behind a debug flag — adds conditional rendering for no real benefit
  at lab scale.

## Decision: Pre-existing sabotage fix

**Decision**: Fix `frontend/src/services/api.ts` line 22 in the same feature
branch. The fallback `??  "http://localhost:3001/bug"` must become
`?? "http://localhost:3001"` so that any local `npm run dev` actually reaches
the backend.

**Rationale**:
- Every acceptance scenario depends on at least one successful round-trip; the
  current fallback routes all requests to a 404 endpoint and produces the same
  "Request failed" UX whether the change is correct or broken.
- Leaving it for a "future cleanup PR" violates Constitution Principle V — the
  two-tab gate cannot be satisfied without this fix in place.

**Alternatives considered**:
- Document it as known-broken and require every reviewer to set `VITE_API_URL`
  — friction with no upside; the fallback exists precisely to avoid mandatory
  env vars at dev time.
- Add a `VITE_API_URL` requirement in README — equivalent to "do not run the
  dev server without env vars," which contradicts the starter's
  zero-configuration `npm run dev` story.

## Open questions

None. All Phase 0 unknowns are resolved. Spec clarifications cover behavioral
ambiguity; the decisions above cover implementation-pattern ambiguity. Ready
for Phase 1.
