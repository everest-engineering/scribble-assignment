# Implementation Plan: Gameplay Interaction

**Branch**: `scribble-lab` *(spec directory `003-gameplay-interaction`)* | **Date**: 2026-06-11 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/003-gameplay-interaction/spec.md`

## Summary

Round 1 already starts and assigns a drawer with a deterministic secret word (feature 002). This feature wires the remaining interaction loop on top of that round:

1. **Guess submission** — a new `POST /rooms/:code/guesses` endpoint accepts `{ participantId, text }`, trims & case-insensitively compares against the active round's `secretWord`, rejects empty/over-long/drawer/already-correct submissions with structured 4xx envelopes, and appends a `Guess` entry to an ordered per-round history.
2. **Scoring** — the room owns a `scores: Record<participantId, number>` map; a correct guess from an eligible guesser increments their score by `100` exactly once per round and locks them out from further guesses in that round.
3. **Snapshot wiring** — `RoomSnapshot.round` is extended with `guesses: GuessView[]`, `scores: Record<string, number>`, and `lockedParticipantIds: string[]`. Every participant sees the same feed and scoreboard via the existing ~2s polling channel. The secret word remains drawer-only.
4. **Drawer canvas** — a drawer-local `<DrawerCanvas />` React component renders an HTML5 `<canvas>` with freehand drawing and a Clear button. **No canvas content is transmitted to the server.** Non-drawers render a placeholder.

This is a pure extension on top of features 001 + 002 — no new dependencies, no new transport, no schema migration (state is still in-memory).

## Technical Context

**Language/Version**: Node.js 20 + TypeScript 5 on the backend; React 18 + TypeScript on the frontend (both already established by features 001 + 002).

**Primary Dependencies**: Express, Zod, `tsx` (backend); React 18, React Router v6, Vite, Vitest (frontend). **No additions.** The drawer canvas uses the platform-native HTML5 `<canvas>` element directly.

**Storage**: In-memory `Map<string, Room>` on the backend (unchanged from feature 001). No persistence.

**Testing**: Vitest in both packages. Pure-helper unit tests + Express integration tests via `fetch` against a live `app.listen` (the pattern established in `backend/src/api/rooms.test.ts`).

**Target Platform**: Backend on `http://localhost:3001`, frontend dev server on `http://localhost:5173`. Modern evergreen browsers with mouse/trackpad input.

**Project Type**: Web application (monorepo with `backend/` + `frontend/` packages).

**Performance Goals**: Polling cadence stays at ~2s (visibility-aware). Guess→feed propagation observed in ≤ 2s in 9 of 10 trials on localhost (SC-001). Canvas rendering is local-only, 60 fps target is moot.

**Constraints**: No WebSockets/SSE, no DB, no auth (per Constitution §I, §II). No new top-level dependencies (per Constitution §IV). All wire types mirrored across `backend/src/models/game.ts` ↔ `frontend/src/services/api.ts`.

**Scale/Scope**: 2–6 participants per room; ≤ 50 guesses per round in normal play. Feed grows in-memory only; rooms are evicted by future cleanup (not in scope).

## Implementation Phases (high level — exact tasks land in `tasks.md`)

### Phase A — Foundation (no behavior change yet)

- Extend `backend/src/models/game.ts` with `Guess`, `GuessView`, and the three new `Round` fields. Mirror in `frontend/src/services/api.ts`.
- Backfill `scores: {}` and `lockedParticipantIds: []` initialisation inside `startRoom` (feature 002 already creates the round).

### Phase B — US1: Submit a guess and see it in everyone's history

- Backend: Zod `submitGuessSchema`, `submitGuess(code, participantId, text)` service function, `POST /rooms/:code/guesses` route, snapshot wiring for `guesses` and `lockedParticipantIds`.
- Backend tests: 400 (empty / too long), 403 (drawer / not in room), 404 (unknown room), 409 (already correct / not in round), 200 path with feed entry.
- Frontend: `GuessPanel` component (input for non-drawers, feed for everyone), `submitGuess()` API call + `RoomStore.submitGuess()` method, wire into `RoundView`.
- Frontend tests: input enable/disable rules, drawer hides input, feed renders ordered entries, no cleartext word leakage in guesser DOM.

### Phase C — US2: Scoring (+100 / +0)

- Backend: extend `submitGuess` to increment `scores[participantId]` by `100` on correct guesses and add `participantId` to `lockedParticipantIds`. Initialise scores to `0` for all participants when the round starts.
- Backend tests: score math, idempotency (lockout prevents double-score), drawer score never changes.
- Frontend: render a scoreboard inside `GuessPanel` (or as a sibling) keyed by participant; visible to everyone.
- Frontend tests: scoreboard rendering, score deltas after a correct guess.

### Phase D — US3: Drawer canvas (drawer-local)

- Frontend: `DrawerCanvas` component with `<canvas>`, pointer event handlers (`pointerdown`/`pointermove`/`pointerup`), and a Clear button. Mounted inside `RoundView` **only** for `state.mode === "drawer"`. **No network calls.**
- Frontend tests: clear button empties the canvas (compare `getImageData` before/after), non-drawer never renders a canvas.

### Phase E — Polish

- Update `README.md` "Implemented today" section with feature 003 highlights.
- Update `CLAUDE.md` to point at this plan (handled at the end of `/speckit.plan` automatically).
- Quickstart pass: two browser tabs, run the scenarios in `quickstart.md`, ensure they pass against the running dev servers.

## Open Policy Decisions (carried forward from `spec.md`)

These three defaults are already encoded above. Confirm or override before `/speckit.tasks`:

1. **Whitespace in comparison**: trim only; internal whitespace preserved (`"rock et"` ≠ `"rocket"`).
2. **Drawer's score**: stays `0` for the active round (drawer cannot guess).
3. **Round termination**: a correct guess does **not** end the round in this slice.
