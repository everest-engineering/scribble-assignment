# Discovery: Room Creation and Join

## Scaffold Analysis (What the Starter Already Had)

The starter provided a runnable but incomplete brownfield scaffold:

- **Backend**: Express server with four endpoints (`GET /health`, `POST /rooms`, `POST /rooms/:code/join`, `GET /rooms/:code`) and an in-memory `Map<string, Room>` store.
- **Frontend**: Vite + React + TypeScript with page routing, branded landing screen, and placeholder pages for Create Room, Join Room, and Lobby.
- **UI Shell**: Lobby displayed participants but only via a manual "Refresh" button.
- **Data model**: `Room` had `code`, `participants`, `createdAt`; no host tracking, no status, no cleanup.
- **API bug**: `frontend/src/services/api.ts` had an erroneous `/bug` suffix in `API_BASE_URL` (`http://localhost:3001/bug`), causing all API requests to 404.

## Gaps (Incomplete Behaviors)

1. **No host designation**: The room creator is not tracked as the host. There is no `hostParticipantId` field on `Room`, so host-only actions (e.g., start game) cannot be enforced.
2. **No automatic lobby polling**: The lobby only updates when the user clicks "Refresh Room." There is no `setInterval` polling loop, so new joiners do not appear automatically.
3. **No game start endpoint or logic**: The backend has no `POST /rooms/:code/start` endpoint, and the frontend `LobbyPage` has a non-functional "Start Game" button that does nothing.
4. **No backend name validation**: `POST /rooms` and `POST /rooms/:code/join` accept empty or whitespace-only `playerName` values without rejection, allowing garbage data into the room.
5. **No room cleanup**: Rooms persist forever in the `Map` even when empty or idle. There is no mechanism to delete abandoned rooms, creating a memory leak.
6. **No clear join rejection messages**: Invalid or non-existent room codes return a generic 404 with no user-facing explanation.

## Assumptions

- **Assumption A1**: Room codes are exactly 4 uppercase alphanumeric characters, generated by the existing `generateCode()` helper, and are unique within the in-memory store.
- **Assumption A2**: Player names do not need to be globally unique; duplicate names within a room are acceptable and do not cause functional issues.
- **Assumption A3**: A browser refresh is treated as a brand-new session with no reconnection or recovery mechanism; the player must re-create or re-join.
- **Assumption A4**: The evaluation expects HTTP polling at approximately a 2-second interval, matching the stated requirement, rather than manual refresh.
- **Assumption A5**: Only one round will be implemented per game, so no rotation logic, timers, or multi-round state is needed in this feature.

## Open Questions / Unknowns (Resolved)

- Q: How should the host be identified for start-game enforcement? → A: Add `hostParticipantId` to `Room`; compare against `participantId` sent in request body.
- Q: What happens if the host leaves before starting? → A: Transfer host to the next earliest-joined participant (FIFO).
- Q: What is the polling failure behavior? → A: Silently retry on the next interval; no visible error UI.
