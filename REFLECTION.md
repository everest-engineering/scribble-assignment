# Reflection Report

## What did the starter app already have?

The starter provided a working scaffold with:
- **Backend**: Express + TypeScript server with 4 API endpoints (`GET /health`, `POST /rooms`, `POST /rooms/:code/join`, `GET /rooms/:code`) and in-memory room storage
- **Frontend**: Vite + React + TypeScript client with routing (Start, CreateRoom, JoinRoom, Lobby, Game), a RoomStore (Context + `useSyncExternalStore`), and placeholder UI components
- **Data**: 5 starter words (`rocket`, `pizza`, `castle`, `guitar`, `sunflower`) and 2 roles (`drawer`, `guesser`)
- **Basic UI**: Card, PageHeader, RoomCodeBadge components with minimal CSS

What was missing: host tracking, lobby polling, game start, drawer assignment, secret word visibility, drawing interaction, guess submission, scoring, result state, and restart/new-round flow.

## What did you add?

**Scenario 1 — Room Setup & Lobby**: Host tracking (`hostId` on Room), host-only start button, minimum 2-player validation, automatic lobby polling (~2s), descriptive error messages for join failures (room full, game in progress, room not found), empty player name validation (frontend + backend Zod schemas).

**Scenario 2 — Game Start & Drawer Flow**: `POST /rooms/:code/start` endpoint, drawer role assignment (host becomes drawer), deterministic secret word selection from starter list via room-code checksum, drawer-only word visibility in snapshots, pending-state UI for non-playing roles.

**Scenario 3 — Gameplay Interaction**: Interactive drawing canvas with stroke submission (`POST /rooms/:code/draw`, `DELETE /rooms/:code/draw`), canvas polling, guess submission (`POST /rooms/:code/guess`) with trimming/case-insensitive comparison/empty rejection, guess history synced via polling, scoring (100 pts per correct guess), drawer-only draw/clear permissions.

**Scenario 4 — Result, Restart & Final Validation**: `round_end` state with results view (secret word revealed, scores, correct guessers), host-only "Back to Lobby" action (`POST /rooms/:code/return-to-lobby`), multi-round support with drawer rotation (round-robin via `currentDrawerIndex`), word cycling through starter list, cumulative score preservation, `game_over` state with final standings ranking, leave room (`POST /rooms/:code/leave`) with host transfer to earliest remaining participant.

**Cross-cutting**: 53 backend unit tests, 2 frontend unit tests, Zod validation for all request payloads, error handling middleware returning meaningful HTTP status codes, inline error display on host-action buttons.

## AI Usage

All code was generated by an AI coding assistant (opencode) guided by a constitution and feature specifications. The workflow was: spec → plan → tasks → implement → validate. AI was instructed to follow TypeScript strict mode, avoid `any`, use Zod for validation, and adhere to the polling-first constraint. Each AI-generated change was reviewed before commit.

## Tradeoffs & Decisions

- **Polling over WebSockets**: Keeps architecture simple and testable with curl alone, at the cost of ~2s latency on state transitions. Acceptable per the spec's explicit constraint.
- **In-memory storage**: No persistence means room state is lost on backend restart. Acceptable per the no-database constraint.
- **Deterministic word selection**: Room-code checksum ensures the same room always gets the same word, enabling reproducible testing.
- **Single-round scope per spec**: Out-of-scope features (timers, countdowns, speed bonuses, multiple rounds in advanced forms) were consciously excluded.
- **Round limit = participant count**: Each player draws exactly once. This creates a natural game endpoint with final standings.
- **Host transfer on leave**: Earliest joiner becomes new host, ensuring remaining players can continue. Drawer cannot leave mid-round to prevent game disruption.
